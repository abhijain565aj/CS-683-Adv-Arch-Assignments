\section{Task 1C: SIMD}

\subsection{Baseline Instruction Count}
For a $512 \times 512$ matrix with a kernel size of $K=5$, the naive baseline implementation executed $\sim$1.31 billion instructions.

\subsection{SIMD Implementations}
The convolution algorithm was parallelized using Intel AVX intrinsics . The inner spatial loop was stepped by the SIMD vector width (e.g., 8 floats for 256-bit AVX2) . Both 128-bit (SSE) and 256-bit (AVX2) implementations were evaluated across different matrix sizes to measure vectorization efficiency.

\subsection{SIMD Intrinsics}

\begin{itemize}
    \item \texttt{\_mm256\_setzero\_ps}: Purpose: Initializes a 256-bit accumulator vector to zero . Justification: Needed to clear the parallel accumulator state before summing the kernel convolution .
    \item \texttt{\_mm256\_loadu\_ps} / \texttt{\_mm256\_storeu\_ps}: Purpose: Loads/stores 8 continuous floats to/from memory . Justification: Since the sliding window shifts by 1 pixel at a time, memory alignment on a 32-byte boundary is impossible to guarantee. Unaligned memory instructions are strictly required .
    \item \texttt{\_mm256\_set1\_ps}: Purpose: Broadcasts a single kernel weight into all 8 lanes of the SIMD register . Justification: During a single kernel step, the same weight must be multiplied simultaneously against 8 adjacent spatial input pixels .
    \item \texttt{\_mm256\_fmadd\_ps}: Purpose: Fused multiply-add . Justification: Highly efficient operations that multiply the input vector by the weight vector and add it to the accumulator in a single hardware instruction cycle, halving arithmetic overhead .
\end{itemize}

\subsection{Analysis}
SIMD instructions massively reduced the executed instruction count. As expected, 128-bit SIMD processing 4 floats per cycle reduced instructions by approximately $4.4\times$, while 256-bit SIMD processing 8 floats reduced instructions by an impressive $8.3\times$. This corresponds closely to the theoretical maximums.

Interestingly, while 256-bit SIMD halved the instructions compared to 128-bit, the raw speedup didn't strictly double. At a $1024 \times 1024$ image size, 256-bit only offered a marginal speedup advantage over 128-bit ($7.74\times$ vs $7.10\times$). This indicates that at high instruction-level parallelism, the CPU becomes heavily bound by memory bandwidth (the L1 cache latency) rather than pure arithmetic throughput. 

\subsection{Questions}

\begin{enumerate}
    \item \textbf{How did the instruction count change?} \\
    The instruction count plummeted precisely in line with the vector widths: 128-bit SIMD divided instructions by $\sim$4.4, and 256-bit divided them by $\sim$8.3 compared to the naive baseline.
    \item \textbf{Did you achieve speedup? Why?} \\
    Yes, a massive speedup of around $7\times$ to $8\times$ was achieved. This was almost entirely due to data parallelism (fused multiply-add computing multiple pixels per cycle) and the drastic reduction in loop maintenance branch instructions.
    \item \textbf{Which SIMD intrinsics were used and why?} \\
    We primarily used \texttt{\_mm256\_loadu\_ps} for unaligned memory reads, \texttt{\_mm256\_set1\_ps} to broadcast scalar weights to all vector lanes, and \texttt{\_mm256\_fmadd\_ps} to execute the core accumulation mathematically efficiently. Unaligned load/stores were necessary because of the overlapping nature of 2D sliding windows .
\end{enumerate}
