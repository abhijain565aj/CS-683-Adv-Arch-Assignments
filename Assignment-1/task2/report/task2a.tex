\section{Task 2A: Software Prefetching}

\subsection{Experimental Setup}

\begin{itemize}
    \item CPU: Intel x86 architecture (Tested on HP Pavilion Laptop)
    \item Matrix dimensions: $128 \times 128$ to $2048 \times 2048$
    \item Prefetch distances: 16, 64, 128, 256, and 512 floats
    \item Cache fill levels: T0, T1, T2, NTA
    \item Performance counters: \texttt{instructions}, \texttt{cpu\_core/L1D.REPLACEMENT/}, \texttt{l2\_rqsts.miss}, \texttt{LLC-load-misses}, \texttt{sw\_prefetch\_access.any}
    \item Number of runs: 1 warmup, 3 timed repetitions
\end{itemize}

\subsection{Matrix Size Analysis}

As the matrix size increases from $128 \times 128$ up to $2048 \times 2048$, the relative performance of software prefetching highly depends on whether the CPU's hardware prefetchers are enabled. When hardware prefetchers are ON, software prefetching causes a slight regression (speedup $< 1.0$), as the manual prefetch instructions merely pollute the pipeline while the hardware is already fetching data optimally. 

However, when hardware prefetchers are turned OFF, software prefetching achieves massive gains. The speedup steadily scales with matrix size, climbing from $1.67\times$ at $N=128$ up to an impressive $2.05\times$ at $N=2048$. This proves that for large memory working sets, manually issuing prefetch instructions effectively hides the memory latency bottleneck that would otherwise stall the FPU.

\subsection{Prefetch Distance}

The prefetch distance determines how far ahead the CPU attempts to fetch memory into the cache. Across the sweep, a very short prefetch distance of 16 floats (equivalent to just 1 cache line) yielded the best geometric mean performance across sizes. Because we are cache-blocking the matrix multiplication, the working set is already highly localized. Requesting data too far in advance (e.g., distance 512) causes data to be fetched and subsequently evicted before the FPU actually reaches it.

\subsection{Cache Fill Level}

The cache fill level dictates which level of the cache hierarchy the prefetched data is loaded into. Taking the geometric mean across all matrix sizes, the \texttt{T0} level (fetching data into all cache levels, including L1) provided the optimal overall results. Because matrix multiplication aggressively reuses data within the inner loops, fetching directly into the L1 cache (\texttt{T0}) minimizes latency to the FPU. Bypassing the cache (\texttt{NTA}) generally performs poorly here as it forces redundant fetches from main memory on repeated accesses.

\subsection{Hardware Prefetchers}

As clearly visualized in Figure \ref{fig:hw_prefetch}, the interaction with hardware prefetchers completely dictates the viability of software prefetching. When hardware prefetching is explicitly disabled, the FPU starves on cache misses, allowing our software prefetching to generate over a $2.0\times$ speedup at large matrix sizes. However, modern hardware prefetchers are highly optimized for sequential memory access patterns; when left enabled, they perfectly hide the latency on their own, meaning our manual \texttt{\_mm\_prefetch} calls merely introduce instruction overhead (resulting in a speedup $< 1.0$).

\subsection{Questions}

\begin{enumerate}
    \item \textbf{What trend is observed in speedup with matrix size?} \\
    When hardware prefetchers are off, the software prefetch speedup scales positively with matrix size, climbing from $1.67\times$ at $N=128$ to $2.05\times$ at $N=2048$, as larger working sets increasingly expose the memory bandwidth bottleneck.
    
    \item \textbf{What is the best prefetch distance?} \\
    Based on the geometric mean across all evaluated sizes, a highly localized prefetch distance of 16 floats (1 cache line) was the optimal configuration.
    
    \item \textbf{At what cache fill level is maximum speedup achieved?} \\
    The \texttt{T0} cache fill level achieved the maximum geometric mean speedup, as it actively pulls the heavily reused matrix blocks into the L1 data cache where the scalar arithmetic units can access them immediately.
\end{enumerate}
