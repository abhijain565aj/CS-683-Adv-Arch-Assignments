\section{Task 2A: Software Prefetching}

\subsection{Experimental Setup}
\begin{itemize}
    \item CPU: Intel x86 architecture (Tested on HP Pavilion Laptop)
    \item Matrix dimensions: $128 \times 128$ to $2048 \times 2048$
    \item Prefetch distances: Swept across multiple values; 32 floats (2 cache lines) identified as optimal
    \item Cache fill levels: T0, T1, T2, NTA
    \item Performance counters: \texttt{instructions}, \texttt{cpu\_core/L1D.REPLACEMENT/}, \texttt{l2\_rqsts.miss}, \texttt{LLC-load-misses}, \texttt{sw\_prefetch\_access.any}
    \item Number of runs: 1 warmup, 3 timed repetitions
\end{itemize}

\subsection{Matrix Size Analysis}
As the matrix size increases from $128 \times 128$ up to $2048 \times 2048$, software prefetching demonstrates exceptional scaling. Unlike previous assumptions, the new data reveals that software prefetching delivers substantial performance improvements \textbf{regardless} of whether the hardware prefetcher is enabled or disabled. 

When hardware prefetchers are OFF, the speedup scales from $1.69\times$ at $N=128$ up to $2.08\times$ at $N=2048$. Strikingly, with hardware prefetchers ON, the gains are nearly identical, climbing from $1.80\times$ to $2.07\times$. This proves that for large memory working sets with complex strided access patterns (like cache-blocked SGEMM), the native hardware prefetcher alone is insufficient. Manually issuing \texttt{\_mm\_prefetch} instructions perfectly complements the hardware, effectively hiding the memory latency bottleneck that would otherwise stall the FPU.

\subsection{Prefetch Distance}
The prefetch distance determines how far ahead the CPU attempts to fetch memory into the cache. Based on the geometric mean across all evaluated sizes, a prefetch distance of 32 floats (equivalent to 2 cache lines) yielded the best overall performance. Because we are cache-blocking the matrix multiplication, the working set is highly localized. Requesting data too far in advance causes data to be fetched and subsequently evicted before the FPU actually reaches it.

\subsection{Cache Fill Level}
The cache fill level dictates which level of the cache hierarchy the prefetched data is loaded into. Taking the geometric mean across all matrix sizes, the \texttt{T1} level provided the optimal overall results. Fetching into the L2/L3 caches (\texttt{T1}) rather than forcing everything into L1 (\texttt{T0}) likely reduces L1 cache thrashing. It keeps the blocked data close enough to avoid costly main memory accesses without evicting immediately useful variables from the highly constrained L1 data cache.

\subsection{Hardware Prefetchers}
The interaction with hardware prefetchers shows that modern hardware and explicit software instructions are highly synergistic for this workload. Because matrix multiplication involves jumping across rows and columns depending on the loop bounds, the hardware prefetcher (which excels at simple, linear access patterns) cannot perfectly predict the next required addresses. Therefore, explicit software hints provide a critical performance boost ($\sim 2.07\times$ speedup) even when hardware prefetchers are left ON.

\subsection{Questions}
\begin{enumerate}
    \item \textbf{What trend do you observe in speedup with different matrix sizes?} \\
    Speedup scales positively with matrix size in both hardware-prefetcher configurations (ON and OFF). It steadily climbs from $\sim 1.7\times$ at $N=128$ to a peak of $\sim 2.08\times$ at $N=2048$. As the matrix size grows beyond the capacity of the L2/L3 caches, the memory bandwidth bottleneck becomes more pronounced, which makes software prefetching increasingly beneficial.
    
    \item \textbf{What is the best prefetch distance?} \\
    Based on the geometric mean across all evaluated sizes, 32 floats (which translates to 2 cache lines) is the optimal prefetch distance.
    
    \item \textbf{At what cache fill level do you achieve the maximum speedup?} \\
    The \texttt{T1} cache fill level achieved the maximum geometric mean speedup. This prevents L1 cache pollution while staging the heavily reused matrix blocks safely in the mid-level caches for quick access.
\end{enumerate}
